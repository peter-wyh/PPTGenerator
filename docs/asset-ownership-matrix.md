# PPTGenerator 四维资产的配置归属与业务线差异化能力
## （第 7 节，配合 agent-architecture-report.md / prompt-refactor-mapping.md）

日期：2026-09-03 ｜ 数据佐证：6 业务线现状（FT=1 指南、DG=3、DM=3、KN=1、SM/CX=0）

---

## 7.1 一张表回答：谁配置什么、差异化在哪一层

| 维度 | 谁来配置/管理 | 在哪配 | 变更频率 | 支持业务线差异化？ |
|---|---|---|---|---|
| **① 提示词** | **平台工程**（代码评审，git 管理） | ai-generate.service.ts → 收缩后独立版本化文件 | 季度级 | **否——全业务线共享**，差异化能力刻意为零 |
| **② Skill（指南）** | **业务运营自助**（后台表单） | Guide Registry（v2 Revision 化） | 周级 | **是——主差异化层**：按 businessLineId + scenario 双键匹配 |
| **③ 文件（assets）** | 业务运营提供素材 + 工程/运营挂载 | skill assets（样张/token/checks） | 月级 | **是**：样张和 token 挂在具体指南下 → 间接按业务线隔离 |
| **④ 工具** | **平台工程**（代码） | Agent Runtime | 月级 | **框架通用 + 参数差异化**：checks 断言清单来自各指南 → 断言内容随业务线变，校验器本身不变 |
| **⑥ 用户提示词** | 最终用户 | 生成表单 | 每次生成 | 任务级差异，与业务线无关 |

**核心答案**：业务线差异化的主战场是 **② Skill**，辅助战场是 **③ 文件**（挂在 skill 下）和 **④ 的断言参数**（来自 skill）。①提示词是全业务线的"宪法"，刻意设计为不差异——凡是要按业务线分叉的规则，都不该写在 ① 里。

---

## 7.2 为什么 ① 必须零差异化

1. **铁律的权威性来自全局一致**：禁伪造/禁品牌禁语/语言规则是对广告主的承诺，某业务线"豁免"即全线失信
2. **回归成本**：① 是共享代码路径，26K 时代改一处全线冒烟；若允许业务线覆盖 ①，测试矩阵 = 业务线数 × 段落数
3. **历史上已经踩过坑**：DM deck 被白色 L1 淹没 → 解法是 overridesVisual 让 L2 接管，而不是给 DM 单独一份 system prompt——差异化应该在"层"上做，不是在"全局"上做

**允许的唯一例外**：`max_tokens` / 超时等运行参数，可按业务线覆盖（配置项，非提示词文本）。

---

## 7.3 ② Skill：差异化的三把钥匙（现有机制 + v2 强化）

现有 6 业务线实证了三种差异化形态：

**钥匙 1：视觉层（isDefault 恒注入）——"我长什么样"**
- FT/DG/DM/KN 各有 1 份视觉规范；SM/CX 为 0 → 走默认中性主题
- 差异化粒度 = 业务线（businessLineId 单键）

**钥匙 2：结构层（scenario 选择）——"我分几章怎么讲"**
- DM 有 3 份（含 Performance Deck overridesVisual）、DG 有 3 份（含经典版式）
- 差异化粒度 = 业务线 × 场景（双键）——同一业务线的月报和 deck 可以是两套完全不同的结构

**钥匙 3：overridesVisual——"强版式接管一切"**
- deck 类场景声明自带视觉 → L1 不注入。这是"场景级整体差异化"的逃生舱

**v2 强化（对业务开放的配置面）**：
- Revision 化：业务改指南不再怕改坏（回滚=切指针）
- checks 断言进指南：业务自己声明"我的报告必须长什么样"（slide 数/必含类名），校验自动执行
- assets 挂载：业务上传样张 → few-shot 注入 → 像素级差异化不依赖工程

**业务运营的自助边界（建议写进权限）**：能改指南正文/checks/挂样张；不能改 ①/④ 的代码，不能改 CONFLICT RULE 裁决逻辑。

---

## 7.4 ③ 文件：差异化的载体而非入口

| 文件 | 谁管理 | 差异化方式 |
|---|---|---|
| 样张 HTML | 业务提供，随指南挂载 | 每业务线/场景一份标杆 → 注入 few-shot |
| tokens.css | 业务提供色板，工程初挂 | Tailwind 模板占位符按业务线填充 |
| tailwind/css-classes/tech-stack 模板 | **平台工程**（共享模板） | 模板共享，值差异化（占位符机制） |
| data-anchor-spec | 平台工程 | 全局统一，零差异 |

注意：③ 里"共享模板+占位符"模式（tailwind-template.md 的 `<EXACT hex>`）是关键设计——**结构共享、值差异化**，避免每个业务线维护一份完整拷贝（拷贝会漂移）。

---

## 7.5 ④ 工具：一个校验器，N 套断言

- preflight/fetch/validate/save 五个工具本身**全业务线一套**（工程维护）
- validate 检查什么 = 读当前指南的 checks 段 → **断言内容随业务线/场景变化**
- 例：DM deck 的 checks 说 slide_count==4，DG 经典版式的 checks 说 section 数≥6 且无 slide——同一个 validate 工具执行两套标准
- 运行参数（max_tokens/重试次数）可按业务线覆盖，属于配置不属于代码

---

## 7.6 决策树：新增/修改一条业务线差异时改哪里

``需求出现`` → 问：这是不是所有业务线都必须遵守的红线？
├─ 是 → ① 提示词（工程改，全量评审+冒烟）
└─ 否 → 问：是"长相/结构/语调"差异吗？
   ├─ 是 → ② 指南（业务后台自助，选对 businessLineId+scenario）
   │        └─ 需要像素级基准？→ 顺带挂样张 asset（③）
   │        └─ 需要"必含/禁含"硬校验？→ 写成该指南的 checks 断言
   ├─ 是"色值/字体值"差异 → ③ tokens 文件（业务给值，占位符机制）
   └─ 是"数据从哪来/图表怎么算"差异 → ④ 工具参数或 mapper 配置（工程改）
```

**反例警示**：不要为业务线复制一份完整 system prompt；不要在 ① 里写 `if (业务线==DM)` 式规则——
它们都会让共享层退化成 N 份漂移的拷贝（配置拷贝必然漂移）。

## 7.7 现状 → 目标的配置权移交清单

| 现状 | 目标 | 动作 |
|---|---|---|
| 指南正文后台可改但无版本无校验 | Registry + 干跑门禁 | v2 Phase 2 |
| checks 只存在于指南散文里（"逐项核对"） | 断言化，业务可自助维护 | Phase 1 MVP（工程代录）→ Phase 2 开放自助 |
| 样张只存在于 Example/ 目录，AI 看不到 | 挂载为 skill asset + few-shot/read | Phase 2 |
| Tailwind/CSS 模板硬编码在 ① | 占位符模板文件 + token 填充 | Phase 1 |
| SM/CX 无指南走中性主题 | 保持（空指南=默认 Skill 兜底，无需强制配） | 无动作 |

## 8. 指南作为聚合根：可以包下 skill、文件、工具吗？

**结论：可以，且正是 v2 的推荐形态——指南升级为"业务线差异化的聚合根"（aggregate root）。
但边界要精确：指南包的是 skill 的内容、文件的引用、工具的配置；不包工具的实现。**

### 8.1 三样东西分别怎么"包"

| 被包对象 | 包法 | 落在 GuideRevision 的字段 |
|---|---|---|
| Skill（程序性知识） | 指南正文本身就是 skill——不用"包"，它就是 | `content`（Markdown 正文，L1/L2 职责标注保留） |
| 文件（样张/token/清单） | **引用挂载**：revision 存 assets 数组，每项 = 引用 + 内容快照 | `assets: [{kind: sample|tokens|checklist, ref, snapshot_hash}]` |
| 工具（校验/参数） | **配置注入**：断言清单 + 参数覆盖，运行时喂给平台工具 | `checks: [{assert, severity}]`、`toolParams: {max_tokens, retries}` |

### 8.2 为什么工具"实现"不能进指南（三条硬理由）

1. **安全**：工具实现 = 可执行逻辑。业务后台若能写逻辑，等于给运营开了一个注入任意代码的口子（生成链路能读 DB、出外网，攻击面实在）。
2. **工程质量**：工具需要测试、评审、随代码版本管理（git）；指南是数据，随 Revision 管理。两套生命周期强行合并，两边都做不好。
3. **可比性**：validate 校验器全业务线一套，效能看板的横向对比才成立。各业务线自带校验器 → 指标失去公约数。

**参数化解决 90% 的差异化需求**：断言内容（slide 数/必含类名/禁含元素）、阈值（重试次数）、开关（某工具对该场景禁用）、预算（max_tokens）——这些放 `checks` / `toolParams`，由平台工具消费。真正遇到参数表达不了的需求（如全新数据源），那是工程排期做新工具/新 mapper，不是指南配置问题。

### 8.3 聚合根带来的四个一致

以指南为唯一管理单元后：

1. **版本一致**：Revision 快照同时固化正文+assets+checks → "当时那次生成用了哪版指南、哪个样张、哪套断言"完整可复现（快照存 hash，文件本体不可变存储）
2. **回滚一致**：切指针 = 正文、样张、断言一起回滚——不会出现"正文回滚了断言还是新的"的半吊子状态
3. **权限一致**：指南可写 = 业务线自助边界，一条权限规则管完（8.2 的三条硬理由反过来保证了这个边界是安全的）
4. **A/B 一致**：两个 Revision 各生成一次 = 同时对比结构+样张+断言的联合效果

### 8.4 什么不进指南（防漂移清单）

| 不进 | 在哪 | 理由 |
|---|---|---|
| 共享模板（tailwind-template / css-classes / tech-stack / data-anchor-spec） | 平台层文件，指南只引用 | 每业务线拷贝一份必然漂移（7.4 占位符模式） |
| 工具代码 / CONFLICT RULE / postProcess 管道 | 平台代码 | 8.2 |
| campaign 数据 | 数据层，工具拉取 | 数据有自己生命周期，混进指南会污染版本语义 |
| 用户意图 | 用户提示词 | 任务级，每次生成都不同 |

**口诀：指南包"这份业务线怎么做事"，平台包"所有业务线怎么把事做成"。**

### 8.5 运行时解析链（Assembler 视角）

```
resolvePairForCampaign(campaignId, guideId)
  → Registry 取 active Revision（正文+assets+checks 快照）
  → mergeGuideLayers(L1, L2, CONFLICT)          ← skill 内容进 prompt
  → Assembler 用 assets.tokens 填充共享模板占位符 ← 文件间接进 prompt
  → few-shot 注入样张（小）/ 注册 read_skill_asset（大）
  → validate 工具装载 checks + toolParams       ← 配置进工具
  → 工具实现永远来自平台代码                      ← 实现不进 prompt
```

一条链上四种"包"各就各位：内容直进、文件引用解引用、配置注入、实现拒绝。
